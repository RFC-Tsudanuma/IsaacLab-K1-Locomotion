## 2. パイプラインの構造

```
Stage 1 walk phase   (5000)  ボール無し・歩行のみ
  → Stage 2 loop_pass  (5000)  限定レンジの蹴り
  → Stage 3 loop_360   (5000)  全方位 + 回り込み
  → Stage 4 long_pass  (10000) 速度帯を (2.0,3.0) → (3.2,5.0) へ
```

`./scripts/rsl_rl/train_walk_long_pass.sh`。`STAGE=4` で Stage 4 だけ回せる。
段の間は `--load_pretrained` (`--resume` ではない。experiment_name が段ごとに違い、
かつ `--resume` は `common_step_counter` を同期してカリキュラムを壊す)。

* 全段が **履歴入力 (H=100 フレーム × 55 次元)**。Stage 1-3 も専用タスク ID
  (`walk_long_pass_stages_env_cfg.py`) で、共用タスクとは別系統。
* 段が繋がったかは起動ログの `Loaded N tensors` で確認する。**29/29 が正常**
  (actor 16 + critic 12 + std 1)。

## 3. 最初の事故と、その再発防止

Stage 4 が「歩くだけで蹴らない」になった当初の原因は報酬ではなく **2 つの環境不備**
だった。切り分けは常に「報酬より先に、本当に継承できているか」を見ること。

### 3.1 actor が 1 本も引き継がれていなかった

共用タスク (1 フレーム観測) の checkpoint を履歴入力タスクへ `--load_pretrained` で
渡すと、actor の重みは名前も形も違うので **黙って全部捨てられる**。critic と正規化統計と
std だけが載り、actor は乱数のまま学習が始まる。ログ上は正常に見える。

→ `train.py` に **actor が 1 本も載らなければ例外で止める** ガードを入れた
(`--allow_untransferred_actor` で明示的に無視できる)。
1 フレーム checkpoint からは `--warm_start_from_single_frame` で移植できる
(旧重みを最新フレームの列に置き、残りをゼロにする。初期出力が旧ポリシーと一致)。

### 3.2 `--reset_noise_std 0.3`

継承元の収束 std は 0.06-0.095 で、0.3 はその 3-5 倍。**これだけで歩行が壊れる**。
実測: 12 iteration で base_height 終了 0.82 / kick_rate 0.19 止まり。外すと
14 iteration で kick_rate 0.99 に復帰。→ 既定で付けない。

### 3.3 診断の型

1. `Loaded N tensors` が 29/29 か
2. 最初の 20 iteration の `base_height` 終了率。継承できていれば 0.03 前後。
   **0.8 まで上がるなら「歩けていない」のであって「蹴らない」のではない**
3. `Policy/mean_noise_std` が継承元 (0.06-0.095) から跳ねていないか

## 4. 報酬設計で分かったこと

### 4.1 キックは常に「残りの歩行報酬を捨てる」コストを払っている

`kick_finished` が latch の 2 秒後にエピソードを終わらせるので、蹴ると歩行報酬の
受け取りが止まる。**この構造がすべての「蹴らなくなる」失敗の根**にある。

観測された発現は 3 通り:

| きっかけ | 何が起きたか |
|---|---|
| 速度帯を一段で (2.0,3.0)→(3.2,5.0) に張り替え | 1200 iteration で kick_rate 0.997 → 0.037 |
| キック報酬をフェードイン (0→500 iteration) | 最初の 500 iteration が「蹴らない方が得」期間になる |
| 歩行が上手くなりすぎた (§4.3) | feet_phase が 2.7 倍になり、蹴るコストが膨らんだ |

対処はそれぞれ、帯のゲート化 (§4.2)、`_freeze_fade_in_curricula` でランプを定数化、
`feet_phase` の減量 (§4.3)。

### 4.2 速度帯は kick_rate ゲートで動かす

`kick_rate_gated_speed_range`。壁時計の線形ランプは「ポリシーが付いてくる」賭けで、
外れると自己回復しない (帯が実力を追い越す → キック報酬が消える → 蹴らなくなる →
帯はさらに上がる)。ゲート版は kick_rate が落ちれば止まり、崩れ続ければ戻る。

実際に機能した記録: ボール位置ノイズ ±0.1 の run で崩壊した際、帯が 5.0 → 4.84 まで
後退して報酬信号が復活し、自力で 5.0 へ戻った。

**弱点**: ゲートは「上げすぎ」は防ぐが「上げる速さ」は制御しない。上限の無い報酬
(`kick_velocity_strong`) と組むと暴走する (§6.1)。

### 4.3 着地 shaping を外したら、歩行が良くなりすぎて蹴らなくなった

`feet_landing_impact` / `feet_landing_vel` / `feet_heel_strike` の 3 項を
long_pass 系列の全段で無効化した (`disable_landing_shaping`)。3 つとも接地イベントの
瞬間だけに効くスパース項で、蹴り足のスイングとは相性が悪い。

歩行そのものは明確に良くなったが、**副作用で Stage 2 が停止した**:

```
Stage 2 で kick_rate 0.19-0.28 のまま 4000 iteration 停滞
kick_elevation_deg 0.97°  (旧 run は同 iteration で kick_rate 0.99 / 15.6°)
それでいて mean_reward は 12.5 (旧 7.7) と高い  ← 蹴らない方が得になっていた
```

原因は `feet_phase` の払い出しが 0.62 → 1.71 と 2.7 倍になったこと。歩容が良く
なるほど「蹴って捨てる報酬」が増える。

→ **蹴りのある段 (Stage 2-4) だけ `feet_phase` の weight を 2.0 → 0.8**
(`rebalance_gait_vs_kick`)。iteration 1400 で kick_rate 0.99 に立ち上がり、
最終的に方向誤差・elevation とも過去ベストを上回った。Stage 1 は歩容の土台なので
下げない。

### 4.4 接近報酬 `walk_speed` が弱すぎた（効果大）

iteration 8000 時点の払い出し:

```
feet_phase      0.200   ← 歩容維持
kick_direction  0.170   ← 蹴りの方向
walk_speed      0.0245  ← 接近を促す唯一の項
```

**接近が歩容維持の 1/8 しか払われておらず、急いで回り込む動機がほぼ無かった**。
2 つの効き方があるので両方いじった:

| 項目 | 変更 | 意味 |
|---|---|---|
| weight | 1.5 → **4.0** | 払い出しの絶対量 |
| `sigma_walk_potential` | 0.5 → **1.0** | `p_walk = exp(-d_to_G/σ)` の減衰幅 |

σ=0.5 だと G から 1 m 離れた時点で p_walk = 0.135 まで落ち、**遠いうちは接近しても
ほとんど払われない**。σ=1.0 で 0.37 になる。

結果 (払い出し 0.025 → 0.124):

| | 蹴るまで | 方向誤差 | 成功率 | 転倒率 |
|---|---:|---:|---:|---:|
| 従来 | 2.80 s | 8.06° | 0.9941 | 1.22% |
| walk_speed 強化 | **2.52 s** | 8.51° | 0.9924 | 1.38% |

**時間ペナルティは使わないこと**。「早く蹴る」を直接報酬にすると回り込みの途中で
蹴る方向に倒れる。強めるのは「早く G へ寄る」だけ。

### 4.5 weight の実体はカリキュラム側にあることが多い

`kick_direction` / `kick_velocity_scaled` / `kick_elevation` / `walk_speed` /
`ball_avoidance` / `extra_ball_touch` は `linear_reward_weight` 系のカリキュラムが
**毎ステップ weight を書き戻す**。`RewTerm.weight` を直接いじっても潰される。
`cfg.curriculum.<term>_weight.params["start_weight"/"end_weight"]` を変えること。

Stage 4 では `_freeze_fade_in_curricula` が start=end に揃えているので、end だけ
変えれば足りる。`kick_velocity_strong` はカリキュラムが無いので直指定でよい。

## 5. sim で勝っても実機で負けた改良（重要）

**sim のメトリクス改善が実機に繋がらなかった例が 2 つある。** どちらも「対称性を
買って安定性と速さを売る」取引になっていた。

### 5.1 蹴り足基準の観測 + P_kick 横オフセット

右足でしか蹴らないため、回り込む向きで蹴りのタイミングが変わる問題への対処。

* 観測 3 番目を `sole_pos` (左足裏) → 右足リンク原点から見たボール位置に置換
* `P_kick` を「蹴り足がボール手前に来る」位置へ横オフセット (量は実測)
* `init_side` 別の左右分割メトリクスを追加

sim では狙いどおり **方向誤差の左右差が 3.64° → 0.03°** になった。しかし実機では
6600 の方が良いと評価された。sim の区間平均で見ても代償が出ている:

| run | 転倒率 | エピソード長 | 速度追従 |
|---|---:|---:|---:|
| 6600 (対策なし) | **1.59%** | **238.7** | **0.911** |
| A+B (蹴り足対応) | 2.51% | 240.8 | 0.884 |
| + p_style k=3 | 2.99% | 245.4 | 0.892 |

### 5.2 p_style を 3 乗

`p_style = clamp(cos(胴体と蹴り方向のズレ), 0, 1)` はキック報酬の係数だが、
cos は正対付近が平坦で **30° ずれても 0.87 (13% しか減らない)**。「あと一歩詰めれば
正対できるのに手前で蹴っても大して損しない」を意味する。3 乗にすると 30° で 0.65。

sim では far/near (必要旋回量 90° 超か否か) の方向誤差差が収束し、
`p_style_at_kick` が 0.878 → 0.936 (素の cos で 16.9° → 12.1°) に改善した。
だが実機では採用されず、転倒率も上がった。

**現在は 3 つとも無効化してある** (`walk_long_pass_env_cfg.py` の `__post_init__` に
コメントアウトで残置)。戻すときは Stage 1-3 と必ず揃えること。

### 5.3 教訓

sim のスコアで勝敗を決めない。特に **転倒率とエピソード長 (蹴るまでの時間)** は
実機の体感に直結するので、方向誤差 0.5° の改善のためにこれらを犠牲にしない。

## 6. 飛距離重視タスク (`...-Power-v0`)

`walk_long_pass_power_env_cfg.py`。Stage 1-3 は共通で、Stage 4 だけ差し替える。

| 変更 | 値 | 理由 |
|---|---|---|
| `kick_velocity_strong` 有効化 | 0.4 × `_KICK_W_SCALE` | `r_direction × v_ball`。**上限が無いので「速いほど得」がそのまま働く**。継承元は None |
| `kick_elevation` 弱化 | 1.5 → 0.75 | 浮き球は仰角のぶん水平成分を削る (30° で 0.87 倍) |
| 速度帯の終点 | (3.2, 5.0) → (4.0, 5.5) | 上限 5.0 ではそれ以上速く蹴る動機が無い |

結果 (6600 比):

| 指標 | 6600 | Power (8500) |
|---|---:|---:|
| 実測水平速度 | 3.73 m/s | **4.30 m/s (+15%)** |
| 距離換算 (a=1.0) | 7.0 m | **9.3 m (+33%)** |
| 蹴るまで | 2.92 s | **2.60 s** |
| 転倒率 | 1.68% | **1.57%** |
| 方向誤差 | 7.16° | 8.17° (+1.01°) |

距離換算は `d = v_h² / 2a`、a ≈ 1.0 m/s² (実機較正 1 点)。

### 6.1 1 本目は崩壊した（weight 0.8 / 帯 6.0）

```
iteration     1000    1400    1800    2000
mean_reward   2.51    3.16    2.02    0.14
転倒率        2.7%    3.8%    4.4%    6.3%
std           0.13    0.14    0.15    0.17
speed_max     3.60    4.08    4.56    4.81
```

**上限の無い報酬とゲート付き帯の相互作用**が原因。「速く蹴れる → kick_rate が保たれる
→ 帯が上がる → もっと速く要求される」が実力を追い越す。std の上昇は PPO が
「今のやり方では報われない」と探索を広げているサインで、崩壊の前兆として使える。

→ weight を半分 (0.4)、帯上限を 5.5 に下げて解決。

### 6.2 `kick_elevation` の weight を下げても仰角は下がらない

半減 (1.5 → 0.75) しても仰角は 22.5° → 20.9° にしかならず、`kick_apex_height` は
むしろ上がった。`kick_velocity_scaled` が `use_3d_speed=True` で **3D 速度**を
測っているため、強く振って浮いても損をしないから。

仰角を実際に下げるなら **目標角そのもの (30°) を動かす** か、
`use_3d_speed=False` にして水平で測る。

## 7. ドメインランダマイゼーション

### 7.1 観測遅延の実装

`walk_kick/mdp/observations.py` の `_delayed_signal`。

* env ごと・エピソードごとに `[0, max]` から一様サンプリングした遅延量
* 過去フレームの**線形補間**で連続値として与える (整数ステップだと 0/1 の 2 値になる)
* **`group` が同じ項は同じ乱数を引く**。同一センサ由来の項が独立に遅れるのは
  物理的にあり得ないため
* `base_delay_s` で固定遅延を上乗せできる (`prev_ball_pos_b` が設計上持っている
  1 ステップとの辻褄合わせに使う)

現在の設定:

| group | 対象 | 遅延 |
|---|---|---|
| `imu` | projected_gravity, base_ang_vel | 0-0.02 s |
| `encoder` | joint_pos, joint_vel | 0-0.02 s |
| `vision` | ball_vel, prev_ball_pos | 0.06-0.10 s (実測カメラ遅延 80 ms) |
| `localization` | kick_direction | 0.01-0.10 s |

### 7.2 ボール位置ノイズは ±0.07 が上限（critic が発散する）

±0.1 (ボール半径 0.11 m とほぼ同じ) で回すと **critic が繰り返し発散**した:

```
±0.1 : value loss > 50 が 230 回、最大 1.26e12、kick_rate < 0.5 への崩壊 102 回
±0.07: 発散 0 回 (10000 iteration 全域)、最大 15.1
```

policy は重くノイズの乗ったボールを見るのに critic は特権情報 (真値) を見るため、
リターンの分散が制御不能になったと解釈している。**±0.07 は今のところ安全な上限**。

### 7.3 自己位置推定の遅延は主因ではなかった

sim では 100 ms / 150 ms は問題なく吸収でき、200 ms から代償が出た
(成功率低下・転倒率 1.8 倍・蹴るまで +0.65 秒)。ただし 200 ms の悪化は
**walk_speed が弱かった時期の測定**で、強化後 (§4.4) は 150 ms でも時間が延びない。

しかし **実機では DR も推論側の時刻補正も効果が見られなかった**。残る gap は別要因
と判断し、遅延は 0.01-0.10 s に戻した。

### 7.4 地面摩擦（現在の実験対象）

継承元は 静 0.4-0.8 / 動 0.2-0.6、`mode="startup"`。地形側が 静 1.0 / 動 1.0 で
`combine_mode="multiply"` なので **実効摩擦はロボット側の値そのもの**。

実機に残る症状:

1. 回り込みの途中で足を早く蹴り出し、芯を捉えられず大きく外す
2. 芯は捉えるが、回り込みすぎ / 足りずに向きがずれる

2 は摩擦ギャップの典型 (旋回のヨートルクは足裏摩擦で作るので、実機の摩擦が違えば
回転量が系統的にずれる)。1 も軸足が滑れば胴体が想定位置に来ない。

→ **静 0.3-1.2 / 動 0.2-1.0 に拡大し、`mode="reset"` に変更**
(`widen_ground_friction_dr`)。startup だと 1 つの env は 1 つの摩擦しか経験せず、
「その場の摩擦を推定して旋回量を補正する」圧がかからない。reset なら強制される。

**ボールの摩擦は固定のまま** (転がり減速 a ≈ 1.0 が距離換算の基準なので動かさない)。

## 8. 推論側 (C++) の知見

`~/booster_k1_locomotion/src/rl_policy_isaaclab_node.cpp`。

### 8.1 キック中のヨー追従

`/localization_result` は 10 Hz で遅い。ノードは Walk→Kick の瞬間に heading を latch し、
以降は 500 Hz の InEKF planar odometry のヨー増分で追従する。これは正しい設計。

### 8.2 アンカーの時刻ずれ（実装済みの修正）

latch 時に `field_yaw_ref` (300 ms 前の測定) と `odom_yaw_ref` (現在) を対応付けて
いたため、**latch 直前 300 ms の回転がキック全体の定常バイアスになる**。
ω=1 rad/s なら 17°。

→ odometry ヨーを**タイムスタンプ付きリングバッファ** (512 サンプル) で保持し、
localization の測定時刻の値と対応付ける (`latency_corrected_anchor`)。
併せて、新しい localization を測定時刻から現在へ外挿してゲイン 0.02 で緩やかに
再アンカーする。

### 8.3 「何も仮定しない」こと

最初の実装は `header.stamp` が使えない場合に **「300 ms 前」と決め打ち**していた。
遅延が実際に無い条件ではこれが 17° の誤差を自分で注入し、**補正をオンにすると精度が
下がる**という現象を起こした。

→ stamp が無ければ補正をスキップ。`now - stamp` が「正かつ 0.6 秒以内」でなければ
別クロック系とみなして無効化。診断用に
`[Kick entry] loc_latency=... anchor_shift=...` を出すようにした。
**遅延の無い環境なら `anchor_shift` は 0 付近でなければならない。**

なお yaw と stamp を別々の atomic から読むと、新しい yaw と前のメッセージの stamp が
組み合わさる競合がある (10 Hz なら 100 ms 分 ≈ 5.7°)。mutex で 1 単位にした。

### 8.4 ONNX の入力は形が同じでも意味が違う

全バージョン `(1, 100, 55)` だが、**観測 3 番目のスロットの中身がバージョンで違う**
(§1)。取り違えても形は通り、静かに性能が落ちるだけなので注意。

## 9. 運用上の落とし穴

| 事象 | 対処 |
|---|---|
| **1 プロセスで env を 2 回作ると Isaac Sim がデッドロック** | 1 タスク = 1 プロセス。実測で 2.5 時間ハングした |
| **ディスクが埋まって学習が落ちる** | checkpoint は 100 iteration ごと ≈ 1.8 MB。10000 iteration で 180 MB。監視に残量チェックを入れる |
| **`pkill -f "train.py ..."` が自分自身を殺す** | 起動シェルのコマンドラインにパターンが含まれる。PID 指定で kill する |
| **print が flush されずログに出ない** | Isaac Sim 経由のスクリプトは `flush=True` を付ける |
| **監視がハングを検知できない** | プロセス生存だけでは不十分。**ログの更新時刻**も見る (10 分更新なしでハング判定) |
| **Isaac Sim が起動 20 ms でクラッシュすることがある** | telemetry プラグイン由来。一過性なので再実行で通る |
| ベスト checkpoint の選定 | `scripts` 外の `best_ckpt.py` (scratchpad) で kick_rate / vel_ratio / dir_err の合成スコア。**飛距離は評価されない**ので Power 系は別途 `vel_ratio × 帯中央` で見る |

## 10. 次にやるべきこと
