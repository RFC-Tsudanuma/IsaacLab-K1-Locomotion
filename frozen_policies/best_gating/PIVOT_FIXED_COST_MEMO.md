# pivot の固定コスト — 計測結果と「外して良い env 側設定」 (2026-11-06)

経路追従セッション (Isaac-Tracking-K1 / w1:pA) からの依頼
「上位方策が pivot を使えるように pivot の固定コストを下げる」への回答。

計測器: `scripts/rsl_rl/eval_pivot_overhead.py` (新規)。ゲーティング方策を台本で
「walk で助走 → mode=turn にして目標角 ±N° → 残り角 5° で mode=walk → 前進 1.0 m/s 指令」
と動かし、**回転時間** (切替から残り角 5° まで)、**再加速時間** (walk に戻してから実速度
0.5 m/s まで)、**転倒率** を分解して測る。256 env・中央値。

```
uv run eval_pivot_overhead.py --headless --num_envs 256 --checkpoint <gating .pt> \
    --entry-speed 1.0 --turn-deg 120 --exit-deg 5
# 旋回 expert 単体で駆動したいときは --force-w 1.0
# expert を差し替えて比べるときは agent.policy.expert_checkpoints.turn=<.pt>
```

## 1. 結論

1. **履歴コマンド枠のゼロ埋めは固定コストの原因ではない。外さないこと。**
   外しても再加速は 1 ステップも速くならず (0.38 s のまま)、転倒が増える
   (停止スタート 0 % → 0 %、1.0 m/s 進入 0 % → 2.3 %)。
   「ゼロ埋めで静止から再加速になる」という見立ては実測では支持されなかった。
2. **最小滞在 0.3 s は 120° 以上の pivot では一度も効かない。** 120° の回転自体が
   0.54 s、180° が 0.70 s かかるので、`min_dwell_s` が切替を遅らせる場面が無い。
   小さな向き直し (< 0.3 s で抜けたい) にだけ効くので、そこを速くしたい場合のみ
   0.1 s 程度へ下げる価値がある (モードのばたつき防止の意味は残る)。
3. **pivot 直後の加速は制限しなくてよい。** walk に戻した瞬間から 1.0 m/s を指令して
   0.26-0.40 s で 0.5 m/s に到達し、98 % の env が到達する。待つ必要は無い。
   ただし**復帰指令を 2.0 m/s にすると逆に遅くなる** (0.36 s → 0.46 s)。静止から
   全速指令を出すと歩行 expert が突っ込んで崩れるため。復帰は 1.0 m/s 程度が最速。
4. **最大の改善は「止まらずに pivot に入れるようになったこと」。** 旋回 expert を
   再学習し、歩行中からの進入で転倒しなくなった (1.0 m/s 進入で 29.7 % → 0 %)。
   減速して止まる時間を上位方策のパイプラインから丸ごと削れる。

## 2. 旋回 expert の再学習 (best_turn: model_7999 → model_9000)

旧 expert は「その場 (立位) から回り始める」分布しか持っておらず、歩行中に pivot へ
切り替えると落ちていた。`K1FlatTurnFinetuneCfg` の `reset_base` 速度ランダム化
(±1.4 m/s) は「立位姿勢のまま滑っている」初期状態でしかなく、本当の進入
(遊脚・歩行中の関節速度・2 秒ぶんの歩行観測履歴) が分布外だった。

対策は `Isaac-Velocity-Flat-Transition-TurnFast` (`K1FlatTransitionTurnFastCfg`) +
`MultiExpertPPO` (learner=turn、歩行 expert を凍結) で 1000 iteration の追加学習。
**歩行 expert が実際に歩いた状態から制御が渡る**ので状態注入は不要。
run: `logs/rsl_rl/k1_transition/2026-11-05_19-39-03_turnfast_v1`。

| 進入速度 | 駆動 | 旧 model_7999 | 新 model_9000 |
|---|---|---|---|
| 0.0 m/s | ゲート | 転倒 1.2 % / 回転 0.80 s | **0.0 %** / 0.72 s |
| 1.0 m/s | expert 単体 (w=1) | 転倒 **29.7 %** / 0.74 s | **0.0 %** / 0.68 s |
| 1.0 m/s | ゲート | 転倒 12.9 % / 0.98 s | **0.4 %** / 0.84 s |
| 1.5 m/s | expert 単体 | (未計測) | 0.4 % / 0.68 s |
| 2.0 m/s | expert 単体 | (未計測) | 1.6 % / 0.68 s |
| 2.0 m/s | ゲート | 転倒 28.5 % / 0.98 s | 0.8-2.0 % / 0.94 s |

立位スタートの能力低下は無く、整定時間も 0.47 → 0.42 s に短縮した。

## 3. 固定コストの内訳 (新 expert、停止スタート、256 env 中央値)

| 回転角 | 回転 | 再加速 (→0.5 m/s) | 合計 | 転倒 |
|---|---|---|---|---|
| 90° | 0.46 s | 0.40 s | 0.88 s | 0 % |
| 120° | 0.54 s | 0.34 s | 0.90 s | 0 % |
| 180° | 0.72 s | 0.38 s | 1.10 s | 0 % |
| 120° (1.0 m/s から進入) | 0.68 s | 0.26 s | 0.94 s | 0 % |

目標「停止 → 180° pivot → 歩行再開の正味オーバーヘッド 0.6 s 以下」について、
定義が 2 通り取れるので両方書く:

* 合計 − 回転時間 (= 再加速そのもの) → **0.34-0.40 s**。どの角度でも目標内。
* 合計 − 0.33 s (そちらが「回転は 0.33 s で足りている」と見ている値) →
  120° で **0.57 s** (目標内)、180° で 0.77 s (目標外)。

180° の回転は実測 0.72 s かかっており、0.33 s というのは turn タスク単体の
`settle_time` (turn モードで既に回り始めている状態からの計測) に相当する。
台本どおり「walk モードから切り替えて 180° 回して 5° 以内に収める」には 0.72 s 必要。
採用基準が 120° 以上の部分集合なら、現状で 0.90 s / 転倒 0 % が出せる。

## 4. env 側設定: 外して良い / 外してはいけない

| 設定 | 判定 | 根拠 |
|---|---|---|
| `zero_command_history_on_switch` | **外さない (有効のまま)** | 外しても再加速は変わらず、1.0 m/s 進入で転倒 0 % → 2.3 % |
| `min_dwell_s = 0.3` | 120° 以上には**無影響**。小角度の向き直しを速くしたいなら 0.1 s へ | 120° の回転が 0.54 s、180° が 0.72 s |
| pivot 直後の加速制限 | **不要 (外して良い)** | 復帰直後に 1.0 m/s 指令で 0.26-0.40 s / 到達率 0.98 |
| 復帰指令を 2.0 m/s にする | **やらない** | 再加速 0.36 → 0.46 s に悪化 |
| `turn_early_exit_rad` (残り 15° で walk) + yaw assist | 停止スタートでは**採用しなくてよい** | 回転 0.72 → 0.66 s だが再加速 0.38 → 0.42 s で合計 1.12 → 1.10 s (1 step 差 = ノイズ内) |
| 歩行中からの pivot 進入 | **解禁して良い** | 1.0 m/s で転倒 0 %、1.5 m/s で 0.4 %、2.0 m/s で 1.6 % (expert 単体) |

## 5. インタフェース

## 6. 採用した成果物 (2026-11-06)

**ゲート重みは据え置き。改善はすべて旋回 expert の再学習から来ている。**

| | |
|---|---|
| ゲート (.pt) | `frozen_policies/best_gating/model_5897.pt` — **従来と同一、再学習は不採用** |
| 旋回 expert (.pt) | `frozen_policies/best_turn/model_9000.pt` (新規) |
| 歩行 expert (.pt) | `frozen_policies/best_walk/model_52700.pt` — 従来と同一 |
| 融合 ONNX | `frozen_policies/best_gating/gating_5897_turn9000.onnx` (新規。expert が焼き込まれるため ONNX は差し替えが必要) |

検証:
* torch 方策との等価性: 64 乱数入力、walk/turn 両モードで `max|Δaction| < 1e-4` (書き出し時の assert)。
* mode=0 パリティ: `best_walk/policy.onnx` と比べて `max|Δaction| = 2.2e-3` 以下
  (w ≈ 1e-3 の残留混合ぶん。従来の採用版と同程度)。歩行単体の挙動は不変。
* mode=1 パリティ: `best_turn/policy.onnx` (= model_9000) と `max|Δ| = 3.8e-4` 以下。
  新 expert が正しく焼き込まれていることの確認。

### ゲート再学習を不採用にした理由 (計測、1024 env 中央値)

| 進入速度 | v4 = model_5897 (据え置き) | v5 = 追加 1200 it | v6 = 追加 800 it (`gate_consistency_coef` 15) |
|---|---|---|---|
| 1.0 m/s 転倒 | 0.20 % | 0.00 % | 0.78 %※ |
| 1.5 m/s 転倒 | 0.68 % | 0.78 % | 1.17 %※ |
| 2.0 m/s 転倒 | **2.05 %** | 4.49 % | 4.30-5.47 %※ |
| 停止→180°→再開 合計 | 1.12 s | 1.10 s | 1.08 s |

※ v6 のみ 256 env。v5/v6 は 1.0 m/s では同等以上だが高速側で明確に悪化するため据え置きを採用。
`gate_consistency_coef` を 5 → 15 にしても `Gate/turn_weight_in_turn` は 0.73 のままで、
これは猶予 15 step 後には w が既に飽和しており (consistency penalty ≈ 1e-4)、
0.73 という平均値が遷移中のランプに引っ張られた数字だったため。**w→1 を強める余地は無い。**

## 8. 追記: 経路追従側での採用判断 (2026-11-06、w1:pA より)

**採用されなかった。原因は pivot の固定コストではなくタスク側の設計。**

`eval_tracking.py --standing --force_pivot_s` (v5a model_1200 + 新 expert、立位 2048 ep)、
初期 |yaw 誤差| ≥ 120° の部分集合:

| | 通常 | 開始 0.8 s の pivot 強制 |
|---|---|---|
| pose | 5.34 s | 5.70 s |
| look | 4.90 s | 5.70 s |

短縮ではなく 0.4-0.8 s の**悪化**。転倒は両方 0.1 % で、進入・復帰の安定性は本メモどおり問題ない。

理由: 上位方策は**後退 (vx -2.0 m/s まで) と曲がりながらの前進**で目標へ進むため、
1.1 s 無進捗になる pivot (回転 0.72 + 再加速 0.38) は停止スタートという最有利条件でも
歩行に負ける。pivot が勝つのは「移動がほぼ無く回転だけ要る」場面に限られ、現在の目標分布
(区間 0.6-2.0 m、後退に罰則なし) ではほぼ出ない。

→ **固定コストをさらに削っても経路追従の採用には繋がらない。** pivot の需要を作るには
上位タスク側 (後退歩行の制限など) の設計変更が必要で、w1:pA がユーザーに提案中。
新 expert 自体は上位方策の再学習 (v7a/v7b) に使われている。
