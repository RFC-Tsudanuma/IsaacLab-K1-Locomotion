# 首（ヨー・ピッチ）安定化 設計書（ドラフト）

## 1. 背景と目的

- 歩行中はカメラが揺れて画像にモーションブラーがかかり、物体検出のbbox位置に誤差が出ている。
- **目的は、露光中のカメラの回転速度を下げてブラーを減らし、bbox位置の誤差を減らすこと**である。
- 画像内で対象が狙った位置から少しずれることは問題にしない。重力基準で正確な方向を向くことも求めない。
- 首はヨーとピッチの2自由度で、ロール軸はない。光軸の向きの揺れは打ち消せるが、光軸まわりの回転（画像ロール）は打ち消せない。

## 2. 要件と制約

1. 上位（意思決定）→ 首制御パッケージ → 歩行プロセス という現在の構成、パッケージの分け方、メッセージ（首の関節角）は**変えない**。
2. 首制御パッケージの2つのモード（凝視：物体の相対位置を指定、角度指定：見渡し）はそのまま使う。
3. 首の関節角は、これまでどおり歩行プロセスが全関節分をまとめてモータに送る。
4. 歩行位相は歩行プロセスしか持っていないので、安定化の推論は歩行プロセス内で、歩行ポリシーと同じ周期（50 Hz）で行う。
5. 安定化のコードは、歩行ポリシーとも首制御パッケージとも分離する。

## 3. 方式

### 3.1 制御量：平滑化胴体姿勢を基準にした視線方向

- 首制御パッケージが出す関節角 `q_cmd` を、「**揺れを除いた平均的な胴体姿勢に対して、この角度を向け**」という指令として解釈する。
- **平滑化胴体姿勢** `R_smooth`：胴体姿勢（ロール、ピッチ、ヨー）にローパスフィルタをかけたもの。ヨーはジャイロの積分でよい（必要なのは短い時間スケールの変化だけなので、ドリフトは問題にならない）。
- **フィルタの設計**：
  - 揺れの最も低い成分は歩行の1周期（左右2歩）の周波数で、ロールとヨーに出る。ピッチはその2倍（1歩ごと）が主になる。フィルタはこの最低周波数を十分に落とす必要がある。
  - 第1候補：**歩行1周期分の移動平均**。周期的な揺れは基本波も高調波もすべて消える。歩行周期が固定（または位相から分かる）なら窓の長さがそのまま決まり、調整するパラメータがない。遅れは窓の半分。
  - 第2候補：2次のローパス（遮断周波数は歩行1周期の周波数の4分の1〜3分の1程度）。歩行周期が変わる場合に使う。1次のローパスは減衰が足りず、揺れの2割程度が基準側に漏れて打ち消されずに残る。
  - **ヨーは遅れを補正する**：旋回中はヨーが一定の速さで変わり続けるので、単純な平滑化では「角速度 × 遅れ時間」だけ基準が遅れ続ける（60°/s の旋回、遅れ0.4 s で約24°）。平滑化したヨー角速度（または歩行コマンドのωz）に遅れ時間を掛けた分を足して補正する。ロールとピッチは値の範囲が限られるので補正は不要。
  - 決め方：歩行中のIMUログにオフラインでフィルタをかけ、平滑化姿勢に歩行周期の波が残っていないことと、旋回や歩き始めでの遅れを確認する。シミュレーションと実機では同じ実装・同じパラメータを使う。
- 目標視線方向：`d_target = R_smooth · FK(q_cmd)`（FK は首の関節角から胴体座標系での光軸方向を求める順運動学）
- 安定化は、実際の胴体姿勢 `R_body` が `R_smooth` からずれた分、つまり歩行の揺れだけを打ち消す。定常的な前傾や意図的な旋回は指令側に残り、今と同じ挙動になる。

### 3.2 関節角の計算

```
q_base = IK(R_body^T · d_target)        … 解析的な逆運動学（ベースライン）
q_neck = q_base + π_residual(obs)       … RLによる残差
```

- 胴体が傾いていると首の各軸も傾くので、ヨーとピッチを独立に補正するのではなく、2自由度の逆運動学を解く。
- 胴体が平滑化姿勢と一致しているとき、`q_base = q_cmd` になる。
- 解析的IKは「今の姿勢」に対する解なので、センサとアクチュエータの遅れの分だけ補償が遅れる。残差はその**先読み**とアクチュエータ特性の補償を担う。
- 特異姿勢（光軸がヨー軸と平行になる向き）は、ピッチの可動範囲内では通常到達しないはず。可動範囲を確認する。

### 3.3 ソフトウェア構成

```
上位（意思決定）
   │ 「見渡せ」「ボールを見ろ」など
   ▼
首制御パッケージ（変更なし）
   │ 首の関節角 q_cmd（メッセージも変更なし）
   ▼
歩行プロセス（50 Hz）
   観測の取得 → 歩行ポリシーの推論
   q_neck = stabilizer.update(q_cmd, IMU, 歩行位相, 首の関節状態)   ← 追加する1行
   全関節の目標をまとめてモータに送信
```

- **安定化ライブラリ**：歩行パッケージにも首制御パッケージにも依存しない、小さな独立ライブラリにする（平滑化フィルタ、FK/IK、方策の重みと推論を含む）。入出力は関節角と観測だけなので、単体でテストできる。
- **歩行パッケージの変更**：ライブラリの呼び出しを1行足し、歩行位相を引数で渡すだけ。指令の意味やモードは歩行側に入らない。
- **無効化フラグ**：無効にすると `q_neck = q_cmd` となり、現在の動作と完全に一致する。段階的に導入でき、実機でオン・オフを比較できる。
- **フェイルセーフ**：安定化の不具合で歩行を止めない。
  - `update` の中で例外を捕捉し、ベースラインのみ、さらに失敗したら `q_cmd` をそのまま返す。
  - 残差の出力と関節目標を範囲内にクリップする。
- **計算時間**：推論（小さなMLP）を足しても制御周期の締め切りを守れることを実測で確認する。
- **指令の届き方**：首制御パッケージの更新周期は50 Hz で、歩行プロセスと同じなので、補間は不要。ただし2つのループは同期していないので、タイミングのずれで同じ指令を2回使ったり、1つ飛ばしたりすることがある。見渡しのように指令が動いているときは、これが1ステップ分の速度の乱れになる。影響が見える場合は、`q_cmd` に軽いローパスか変化率の制限をかける。学習時にも同じ重複・欠落を模擬する（4.6）。
- **見渡しの往復範囲**：可動範囲いっぱいにせず、胴体の揺れの振幅分の余裕を残す。端で関節が飽和すると、そこでは安定化が効かない。

### 3.4 並進（上下動・横揺れ）は補償しない

カメラ位置の揺れによる見かけの動きは補償の対象にしない。理由は次のとおり。

- **bboxへの影響が小さい**：並進によるブラーは対象までの距離に反比例するが、対象の画像上の大きさも距離に反比例する。そのため、対象の大きさに対するブラーの割合は距離によらずほぼ一定で、小さい。

  | 対象までの距離 | ボールの直径 | 回転によるブラー | 並進によるブラー |
  |---|---|---|---|
  | 0.5 m | 約230 px | 約5 px（2%） | 約2.3 px（1%） |
  | 1 m | 約115 px | 約5 px（4%） | 約1.1 px（1%） |
  | 3 m | 約38 px | 約5 px（13%） | 約0.4 px（1%） |

  仮定：胴体の回転による角速度 約50°/s、横揺れ ±3 cm・約1 Hz、露光時間 10 ms、画像の分解能 約10 px/°、ボールの直径 約20 cm。実機の値で計算し直すこと。
  - カメラはグローバルシャッター、60 fps。露光時間は未確認だが、上限は約16.7 ms である。上限の場合、ブラーはすべて約1.7倍になる（回転 約8 px、3 m のボールに対して約22%）。回転と並進の比は露光時間によらないので、結論は変わらない。
- **回転のブラーは遠くの小さい対象ほど相対的に効く**ので、回転の安定化が効果の大部分を占める。
- **並進の補償は1つの距離にしか効かない**：近くのボールに合わせて首を回すと、その回転が遠くの対象には逆にブラーとして乗る。

必要になった場合の拡張：目標を「指令方向の先、距離 d にある点」とし、観測に 1/d を加えて学習し直す。距離はメッセージに任意項目として足すか、光軸と地面の交点から求める。

### 3.5 画像ロールの残り

- 画像ロールは打ち消せない。画像中心から r ピクセル離れた点は、ロール角速度 ω に対して r·ω の速さで動く。
- 凝視時は対象を画像の下から25%程度に置いているので、中心からの距離は画像高さの4分の1程度である。画像高さ480 px、ロール角速度 約20°/s、露光時間 10 ms を仮定すると、ブラーは約0.4 px で無視できる。

## 4. RLによる残差方策

### 4.1 学習環境
- 歩行ポリシーは**固定**し、環境の一部としてシミュレーション内で動かす。
- 歩行コマンド（vx, vy, ωz）はランダムにサンプリングする。歩き始め、停止、旋回の切り替えも含める。
- 安定化ライブラリの平滑化フィルタ、FK/IK は実機と同じ実装を使う。

### 4.2 観測
- 胴体IMU：姿勢、角速度（3軸）と、その短い履歴
- 平滑化姿勢に対する胴体姿勢の偏差
- 首の関節角・角速度（ヨー、ピッチ）
- 指令 `q_cmd`（または胴体座標系での目標方向）
- 前回の行動
- 歩行位相、歩行コマンド

### 4.3 行動
- 首の目標関節角（ヨー、ピッチ）への残差。PD制御で実行する。

### 4.4 報酬

目的がブラーの低減なので、**角速度の項を主**にする。

| 項 | 重み | 目的 |
|---|---|---|
| 光軸の角速度と目標方向の角速度の差（光軸に垂直な成分） | 主 | ブラーの低減。意図的な首振りは罰しない |
| 光軸と目標方向のなす角 | 弱め | 指令から離れていかないようにする |
| 行動変化率 | 小 | 振動の抑制 |
| トルク | 小 | 省エネと発熱の抑制 |

- 画像ロール方向の角速度は制御できないので、報酬に含めない。

### 4.5 評価に使う量
- 露光時間あたりの光軸の回転量（ブラーの代理指標）を、学習中のログにも出す。

### 4.6 指令のサンプリング
- 一定値、ステップ状の変化、見渡しの往復、ゆっくり変化する凝視風の指令を混ぜる。
- 首制御パッケージと同じ更新周期（50 Hz）・遅延で指令を与え、非同期による指令の重複・欠落もランダムに入れる。
- 安定化だけを学習して、素早い首振りへの追従が悪くならないようにする。

## 5. Sim-to-Real 上の注意

- **遅延のランダム化は必須**：残差の価値の大部分は先読みにある。IMU、姿勢フィルタ、アクチュエータの遅延をランダム化しないと、実機で位相がずれて逆効果になる。
- **IMU姿勢推定の品質**：歩行中は加速度センサに歩行の加速度が混ざる。角速度が主な報酬なので、ジャイロの値を直接使える分、姿勢の絶対精度への依存は小さい。
- **平滑化フィルタの遮断周波数**：低すぎると旋回や加減速の開始直後に意図した姿勢変化まで打ち消そうとし、高すぎると歩行の揺れを通してしまう。
- **アクチュエータモデル**：首モータのバックラッシュ、帯域、トルク制限をモデル化またはランダム化する。
- **歩行への影響**：首の動きは頭部質量による重心のずれと、ヨー方向の反トルクを生む。首を固定して学習した歩行ポリシーへの影響を確認する。

## 6. 検討したが採用しなかった案

| 案 | 採用しなかった理由 |
|---|---|
| 重力基準の視線方向（方位・仰角）を指令にする | メッセージと首制御パッケージの変更が必要。目的はブラーの低減で、絶対的な方向の精度は要らない |
| 首制御パッケージを50 Hzで回し、歩行側が位相を公開する | 関節角を歩行プロセス経由で送るので、往復で約1周期の遅延が乗る |
| 歩行プロセスを制御ループのホストにし、安定化をコントローラとして読み込む | 設計としては整理されるが、現在のパッケージ構成からの改造が大きい |
| 指令の解釈（凝視点から角度への変換）を歩行プロセスで行う | 首の指令の意味が歩行側に入り、責務の分け方として不適切 |
| 首を歩行ポリシーの行動空間に含めて一緒に学習 | 上位から首指令を受ける構造と合わず、モジュールも分けたい |
| 歩行位相に基づく適応フィードフォワード | 位相推定と非周期的な場面での切り替えを手で設計する必要がある。比較用のベースラインにはなる |
| 解析的IKのみ（残差なし） | 遅延により、歩行の揺れの周波数では補償が遅れる。ベースラインとして残し、比較対象にする |

## 7. 評価指標（案）

- 露光時間あたりの光軸の回転量（定常歩行、旋回、歩き始め・停止で分けて測る）
- 画像のブラー量の実測（静止時と歩行時の画像の鮮鋭度の比較）
- 歩行中のbbox位置の誤差と検出率（静止した対象に対して、距離別に測る）
- 指令へのステップ応答（立ち上がり時間、オーバーシュート）
- 比較対象：安定化なし、解析的IKのみ、解析的IK＋RL残差

## 8. 未決事項

- カメラの露光時間と分解能の実際の値（3.4、3.5の見積もりを計算し直す）。シャッターはグローバル、60 fps と確認済み
- 露光が自動の場合、固定して短くできるか（ゲインを上げて露光を短くするのは、安定化と独立に効くブラー対策になる）
- 平滑化フィルタの方式（歩行周期が固定なら1周期分の移動平均、そうでなければ2次のローパス）とパラメータ。歩行中のIMUログで決める
- 非同期による指令の重複・欠落が実機で問題になるか（なる場合は `q_cmd` にローパスか変化率の制限を入れる）
- 残差の出力範囲の制限
- 見渡しの往復範囲に残す余裕の大きさ（実機の胴体の揺れの振幅から決める）
- ピッチの可動範囲と特異姿勢の関係
